| 11 | Power loss or a kill during the apply of a sync (G8). The apply writes the pushed tree into the project file by file (D100), so a stop can leave the project with only part of the new files | The ops log saves the phase `apply` before the first write to the project. While that record is open, the project takes no open, no edit and no sync (`sync.apply-pending`); a record whose last save failed keeps its project locked for the rest of that session. The next start runs the same apply again from the scratch copy, then deletes it: the apply compares before it writes, rewrites a journal file that a stopped write left in part, and never removes a journal file. Recovery only goes forward. No sync starts, and no project opens or takes an edit, until `recover()` loads the ops log at that start (`opslog.not-loaded`). A settings document that does not parse cannot lock a project: the next start keeps its bytes under `unreadableSettings`, starts an empty ops log, and shows the incident in the dev Inspector. A store that was open before the apply takes no edit and no checkpoint after it (`sync.project-replaced`). One write costs 0.33 ms to 0.43 ms on the rig (D100 point 6). Proof: the `[G8]` tests in `test/sync/syncOperation.test.ts`: the apply kill sweep (a kill after each write, remake and commit of the apply, and inside each one; the reopen classifies `converged` or `regenerated-forward`, with every own and teammate segment), the kill inside the save of the apply phase, the `applyScratch` sweep over each write, delete, remake and commit, and the stale-store test |
