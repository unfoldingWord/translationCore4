| 11 | Power loss or a kill during the apply of a sync (G8). The apply writes the pushed tree into the project file by file (D100), so a stop can leave the project with only part of the new files | The settings document never locks or unlocks a project; the scratch copy and its marker are the record (D100 point 2). After the push, the sync writes the marker `ingredients/tc4-sync/apply.json` into the scratch copy, applies, deletes the marker, then deletes the scratch copy. At each start (for each repository at any path), and at the start of each sync, a scratch copy with the marker gets the same apply again and is then deleted; a scratch copy with no marker is only deleted. A scratch copy whose project is gone stays on disk, hidden, because the platform lists no `_local_/_archive_/` folder (`list_local_repos.rs:48-50`, pankosmia-web a83725b); it changes no project. While the marker is there, the project takes no open (`sync.apply-pending`). The apply compares before it writes, rewrites a journal file that a stopped write left in part, and never removes a journal file. Recovery only goes forward. No sync starts until `recover()` loads the ops log at that start (`opslog.not-loaded`), because the Report goes there. A settings document that does not parse or that another writer changed has no effect on the recovery: the next start keeps unreadable bytes under `unreadableSettings`, starts an empty ops log, and shows the incident in the dev Inspector. A store that was open before the apply takes no edit and no checkpoint after it (`sync.project-replaced`). One write costs 0.33 ms to 0.43 ms on the rig (D100 point 6). Proof: the `[G8]` tests in `test/sync/syncOperation.test.ts`: the apply kill sweep (a kill after each server call after the push, and inside each one, the marker write, the marker delete and the scratch delete included; the reopen classifies `converged` or `regenerated-forward`, with every own and teammate segment), the concurrent `recordInstalled` write (B1), the settings document torn at restart (B2), the kill inside the scratch delete (B3), the sync that starts while the marker is there, the `applyScratch` sweep over each write, delete, remake and commit, and the stale-store test |
