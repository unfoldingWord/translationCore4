# Open time at the large fixture's scale, over the app's own open path — the issue #95 record

**Date:** 2026-09-05. **Commit:** `6978910` (the tree the measurement ran on; the first commit
of the issue #95 branch `i95-open-progress`, parent `6dc5f61`).
**Machine:** Apple M2 Pro (10 cores), 16 GB RAM, macOS 26.5.1, Node v22.14.0, `pankosmia-web`
0.18.5 rig (git rev `99fd9be`), the Vite dev server (`npm run dev`) at :5199, Chromium via
Playwright 1.61.1.

## What was measured

The rig-backed open through the app's own store — `JournalingStore.open()` over HTTP, the path
a translator's click runs — at the scale of the seeded large fixture, from the click to the opened
book's text on screen. The pull request 96 review asked for this measurement: the earlier
`bench-fold` numbers (`bench-fold-2026-08-25.md`) were the reference reader on disk, a lower bound
with no transport. It is not a measurement of the packaged application (see Limits).

## Method

1. `dev-env/scripts/seed.zsh` seeds `_local_/_local_/sample_burrito_large`:
   `scripts/seed-large-project.mjs` builds Titus with **4,000** saved edits, one journal
   segment each, plus the creation seed and the `book.add` — **4,002 segments**, 2,044,187 bytes
   of sealed segments (average 510 bytes; `stat` over the segments directory) — from the
   reference modules, converged by construction (its own `classifyDivergence` self-check is
   clean).
2. `npx playwright test e2e/j15-slow-open.spec.ts`. The second test clicks the fixture's
   Titus tile on Home, waits for the progress indicator, then for the fixture's last edit text
   (`(edición N)`) in the Draft view, and prints the elapsed wall-clock time. It also records
   every value the indicator showed.
3. The J15 teardown runs the fold-compare verifier on every journaled local project, the
   fixture included.

That each segment is read once per open is proved by the unit test
`test/openProgress.test.ts` ("a fresh open reads every segment exactly once", a spy on
`ServerApi.readIngredient`), not by this run: the journey did not count HTTP requests.

## Result

```
J15 open-time: sample_burrito_large · 4002 segments · 4620 ms click-to-text · stages journal>state>prepare · 96 distinct values, first 5, last 100
  3 passed (19.5s)
```

| Measurement | Result |
|---|---|
| Segments the open listed and read (one scan) | 4,002 |
| Click to book text on screen | **4,620 ms** |
| Per segment, all-in (transport + validation + fold + UI) | ≈ 1.15 ms |
| Distinct progress values shown | 96 (5 → 100) |
| Stages shown, in order | reading the journal → checking the project state → preparing the project |
| Fold-compare verifier on the fixture after the open | verified (teardown green) |

An earlier run on the same tree, before a missing `await` in the spec was corrected, measured
5,135 ms. One machine, two runs; a point estimate, not a median: the criterion this record
serves is that a slow open shows real progress, not a speed target (owner's ruling, 2026-08-25).

## Comparison with the 2026-08-25 projection

`bench-fold-2026-08-25.md` projected the open at "roughly 12 s at NT scale" for 15,945
segments read **twice** (0.319 ms/read × 2, transport only). This run reads once (issue #95's
single scan) and includes validation, the fold and the render: 4,002 segments in 4.6 s, about
1.15 ms per segment all-in. A linear extrapolation gives about 18 s for an aligned New
Testament and about 5.3 minutes for the checked whole Bible (278,041 segments) — with a
determinate indicator throughout. These extrapolations are not measurements.

## Limits

- The fixture's segments are small `text.verse.set` edits (510 bytes sealed on average);
  alignment and decision segments are larger and validate more slowly.
- Development build (Vite dev server, unminified modules), not the packaged application. The
  packaged build is expected to be faster, not slower; it was not measured.
- Not measured: a cold rig process, a spinning disk, a second actor's directory.
