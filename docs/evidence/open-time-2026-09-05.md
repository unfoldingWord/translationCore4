# Production open time at the large fixture's scale — the issue #95 record

**Date:** 2026-09-05. **Commit:** the first commit of the issue #95 branch (`i95-open-progress`,
parent `6dc5f61`); the pull request that carries this file names the exact hash.
**Machine:** Apple M2 Pro (10 cores), 16 GB RAM, macOS 26.5.1, Node v22.14.0, `pankosmia-web`
0.18.5 rig (git rev `99fd9be`), the Vite dev server (`npm run dev`) at :5199, Chromium via
Playwright 1.61.1.

## What was measured

The rig-backed **production open path** — `JournalingStore.open()` through the app, one HTTP
read per journal segment — at the scale of the seeded large fixture, from the user's click to the
opened book's text on screen. This is the "gold-standard measurement" the pull request 96 review
asked for: the earlier `bench-fold` numbers (`bench-fold-2026-08-25.md`) were the reference
reader on disk, a lower bound with no transport.

## Method

1. `dev-env/scripts/seed.zsh` seeds `_local_/_local_/sample_burrito_large`:
   `scripts/seed-large-project.mjs` builds Titus with **4,000** saved edits, one journal
   segment each, plus the creation seed and the `book.add` — **4,002 segments** (16 MiB of
   sealed segments), from the reference modules, converged by construction (its own
   `classifyDivergence` self-check is clean).
2. `npx playwright test e2e/j15-slow-open.spec.ts`. The second test clicks the fixture's
   Titus tile on Home, waits for the progress indicator, then for the fixture's last edit text
   (`(edición N)`) in the Draft view, and prints the elapsed wall-clock time. It also records
   every value the indicator showed.
3. The J15 teardown runs the fold-compare verifier on every journaled local project, the
   fixture included.

| Measurement | Result |

| Click to book text on screen | **5,135 ms** |

| Fold-compare verifier on the fixture after the open | verified (teardown green) |

One run, one machine. The number is a point estimate, not a median: the criterion this record
serves is that a slow open shows real progress, not a speed target (owner's ruling, 2026-08-25).

## Comparison with the 2026-08-25 projection

`bench-fold-2026-08-25.md` projected the production open at "roughly 12 s at NT scale" for
15,945 segments read **twice** (0.319 ms/read × 2, transport only). This run reads once
(issue #95's single scan) and includes validation, the fold and the render: 4,002 segments in
5.1 s, about 1.28 ms per segment all-in. A linear extrapolation gives about 20 s for an aligned
New Testament and about 6 minutes for the checked whole Bible (278,041 segments) — with a
determinate indicator throughout. These extrapolations are not measurements.

## Limits

- The fixture's segments are small `text.verse.set` edits (≈ 4 KB sealed); alignment and
  decision segments are larger and validate more slowly.
- Development build (Vite dev server), not the packaged application.
- Not measured: a cold rig process, a spinning disk, a second actor's directory.
