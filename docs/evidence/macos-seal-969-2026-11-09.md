# The macOS seal after the manifest (#969, 2026-11-09)

Issue #969: `scripts/release/stage.sh` wrote `BUILD-MANIFEST.json` into the app bundle after
signing and verifying it, so every shipped macOS bundle failed `codesign --verify --deep --strict`.
Branch `fix/969-macos-seal` from main 9cfb7b5f: `seal-macos.sh` signs, writes the manifest inside
the bundle, re-signs the app over it and verifies both; `package.sh` and `smoke-installed.sh`
verify again. What ran, where, and what it showed.

Machine: the owner's Mac, macOS 26.5.1 (Apple silicon), Node 22.14.0, `/usr/bin/codesign`;
Electronite `electronite-v37.1.0-graphite-darwin-arm64.zip` from an earlier local build, sha256
`a3dde44e…59488`, the one `stage.sh` pins.

## The regression test, red then green

`scripts/release/seal-macos.test.mjs` seals a small Electron-shaped bundle (a main executable, a
resource, a nested helper app) with the real `seal-macos.sh` and `manifest.mjs`.

- Against a copy of `seal-macos.sh` in main's order (deep sign, verify, then the manifest):
  `not ok 1 - the_sealed_app_passes_codesign_with_its_manifest_inside` with
  `a sealed resource is missing or invalid`; `not ok 2` (no `unrecorded`). Tests 3 and 4 pass
  either way: they prove the checks bite, not the order.
- Against the branch's `seal-macos.sh`: `# pass 4`, `# fail 0`, 0.7 s.

## Packaging and the payload

`scripts/release/package.sh macos-arm64` on main's stage: refused at its new `codesign` check,
exit 1, nothing in `dist`. On the branch's stage: the pkg built; `pkgutil --expand-full` on it,
then on the payload's `translationCore 4.app`: `codesign --verify --deep --strict` passes,
`manifest.mjs --check` reports `121 files match, 2 unrecorded`, and the `BUILD-MANIFEST-macos-arm64.json`
beside the pkg is byte for byte the bundle's.

An independent reviewer repeated the stage, test, package and expand steps with its own stand-ins
and the same outcomes (the seal verifies, `2 unrecorded`, its manifest `100 files match`), and
found that `manifest.mjs` invoked through a symbolic link (such as `/tmp` on macOS) did nothing
and exited 0; fixed in the branch by resolving `argv[1]`.

## In CI

The `release` workflow runs on a push of the branch (run 42640604429). Every `build` job failed
at main's own step "no test hooks in the shipped binary" (`release_has_no_test_hooks`: the
release `tc4` holds `"tc4-seed-batch"` since d5ca2836), before any step this branch changes, so
the macOS `smoke` job, which installs the pkg, verifies `/Applications/translationCore 4.app`
and starts it, did not run. Filed as #971; the smoke evidence for #969 follows once a
release run can reach it.
